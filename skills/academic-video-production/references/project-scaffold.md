# The project scaffold

`references/production-contract.md` defines the folder layout and what `video-plan.json` must
contain. This file covers what a built video puts **inside** that layout: the files the skill
does not ship, why each exists, and what carries from one video of a course to the next. The
conventions were worked out over 25 lessons built with the SmartQuest skill this one was forked
from; they apply unchanged.

The layout as it is actually built, with the additions marked:

```text
~/academic-videos/<COURSE>/<nn>-<slug>/
├── notes/                #   the lecture files, or notes/SOURCE.md pointing at them
├── notes-map.md          #   Gate 1: concepts by slide, notation, verbatim statements, gaps
├── brief.md              #   the design record — per knowledge point the picture, wrong model,
│                         #   aha, examples by role, justifications as the notes name them,
│                         #   the course's colour assignment, the camera decisions
├── make_plan.py          # + AUTHORS video-plan.json. Durations here, everything else derived
├── check_plan.py         # + the contract's invariants, runnable in the project
├── make_script.py        # + emits captions.md from the plan
├── video-plan.json       #   generated. Never hand-edited
├── captions.md           # + the Gate 1 artifact Paco actually reads
├── src/
│   ├── theme_boot.py     # + the only place the theme is switched on
│   ├── kit.py            # + this video's figures, and the course series' memory
│   ├── script.py         #   the scenes
│   └── captions.py       #   generated by build_captions.py — do not hand-edit, not rendered
├── tools/                #   installed by tools/install.py
├── vendor/               # + only when the video is bundled for another machine
├── storyboard/  audio/  out/
└── RENDER-REPORT.md      # + written at delivery
```

`audio/` exists only if a voice was asked for on this video (`audio/voice/`, see
`references/sound-and-voice.md`). There is no narration sheet: with no voice by default, the
captions are the narration and `captions.md` is the script.

## `src/theme_boot.py` — the only place the theme is switched on

```python
import academic_theme as sq
sq.use_light()                  # ← the theme answer given at Gate 1 (omit for dark)
from academic_theme import *    # ← must come AFTER
```

`use_light()` must run **before** the star import, because the import copies the values out. Get
the order wrong and half the video is dark-theme; nothing raises. So every module imports the
palette from `theme_boot`, never from `academic_theme` directly, and the file names in its
docstring which theme was approved at Gate 1.

It also resolves the theme from `../vendor/` when that directory exists and falls back to
`~/.claude/skills/academic-video-production/scripts` otherwise — that one line is what makes a
bundle self-contained.

## `src/kit.py` — the video's figures, and the course series' memory

Every project has one. It holds three things, and the reason it is a file rather than code inside
`script.py` is that all three are exactly what drifts between shots:

1. **The problem band.** When an example works a stated problem — from the notes, a tutorial
   sheet or a homework — its statement is on every shot of that example (hard rule 23), so it is
   built **once**, read from `video-plan.json`'s `question` block, and every scene asks for it by
   question id rather than re-typing the string (contract invariant 12). A re-typed statement is
   how a band changes width halfway through an example. A video with no stated problem has no
   band, and this part of `kit.py` is empty.
2. **The pens.** The colour assignment recorded in `brief.md` is written down once, as names, so
   no scene ever picks a colour by hand (hard rule 6). It is the **course's** assignment, not the
   video's: if the eigenvector is `RESULT` in Lecture 7 it is `RESULT` in Lecture 8.
3. **The apparatus** — the figure builders for this course's discipline: the grid, the vector
   and the unit square for linear algebra; the array with its indices, the tree and the stack for
   an algorithms course; the free-body diagram or the phasor for physics. See the discipline
   table in `SKILL.md` for what "the figure" is in each.

Two conventions that matter more than they look:

**Layout helpers are copied from the previous video unchanged.** `panel()`, `centred()`,
`fit_figure()`, `mrow()`, `derivation_ref()`, `solution_page_ref()` are carried forward verbatim,
not re-derived. A course's videos are one series: a helper that drifts is a helper that puts the
problem statement two pixels left of where it was in the video watched last week. If a helper
genuinely needs to change, change it **and** say which earlier videos of the course now differ
(hard rule 37).

**Every builder returns its parts named, and adds nothing.** A `unit_square()` hands back its
edges, its fill, its corner labels and its area readout as named pieces; the scene decides which
of them are givens (on from the first frame) and which are derived (drawn on the beat that
produces them), because hard rule 18 makes that a per-shot decision. A builder that calls
`self.add()` has taken that decision away.

**The apparatus is established once per course and reused.** The first video of a course builds
the figures its concepts are drawn with; every later video of that course imports them. When a
new video needs an apparatus that exists, import it; when it needs a new one, build it to the
same contract so the next video of the course inherits it.

### What carries over, and between which videos

| From | To | Carries |
|---|---|---|
| The most recent video **of the same course** | the next video of that course | `theme_boot.py`, `kit.py` (helpers **and** apparatus), `make_plan.py`, `check_plan.py`, `make_script.py`, and the colour assignment in `brief.md` |
| The most recent video **of any course** | a course's **first** video | the layout helpers and the plan scripts only. The colour assignment starts fresh — a pen's meaning belongs to one course's series, and borrowing another course's assignment would import meanings that mean nothing here |

Videos of different courses do not share colour meanings and never need to. Within one course
they always do.

## `make_plan.py` — the plan is generated, never hand-edited

Only two kinds of number are authored: **shot durations and cue durations**. Every absolute
timecode, every derived field and the whole JSON are computed from them, so the plan cannot drift
from the script, and a re-timed shot cannot leave a stale `start` three shots later.
`durationSeconds` is their sum — an output, never a target (rule 39).

Two habits worth copying:

- A `STATUS` constant at the top carries the pipeline state into the plan, advanced **only when
  Paco has actually approved the gate before it** — `plan-awaiting-approval`,
  `storyboard-awaiting-approval`, `awaiting-export`, and so on, in the contract's exact strings.
- **Decisions are recorded as comments beside the value they changed.** For example: a problem
  band first measured 24% of frame height against its 22% cap; moving one given from the part
  into the statement — where the tutorial sheet states it anyway — brought it to 20.1% with the
  section tag kept. The mathematics and the answer were untouched. Six months later that comment
  is the only record of why the statement reads the way it does.

## `check_plan.py` — the contract, runnable

A per-project script that re-checks the production contract's invariants against the generated
plan: timeline continuity, whole frames at 60 fps, cue containment, the 4.0 字/秒 budget, the
25% still floor, the 3–4 s title card with its subtitle exactly `[course, "Lecture N"]`, one
chapter per knowledge point, 16:9 at 1920×1080, no CJK outside the three fields allowed to hold
it, every example with a role and each knowledge point's first example concrete, the 4.0 s floor
on a recap page **if** the video has one, and `narration.source` `"none"` unless a voice was
asked for. Run it after every `make_plan.py` run and before every gate. It reuses
`scripts/build_captions.py`'s `weight()` so the 字數 it counts is the same 字數 the caption
builder counts — never re-implement the counter.

## `captions.md` — the Gate 1 artifact Paco actually reads

`make_script.py` emits it from the plan. Per shot: the timecode range, the section tag, the
register, the still time with its percentage, what is on the picture, and a cue table —
時間 · 秒 · 字數 · 字/秒 · 中文（書面語）· English. The dashboard's Gate 1 card finds it by that
name (`tools/build_dashboard.py`).

Which numbers are gates and which are house style, because reporting the wrong one is its own
failure (hard rule 35):

| Number | What it is |
|---|---|
| **4.0 字/秒** | the gate — `check_plan.py` fails the plan above it |
| **25% still** | the gate — contract invariant 6 |
| 3.5 字/秒 | house style: captions are *authored* here, because Paco is reading **and** watching — the slack is for the eye going back to the figure |
| ≤ 90% caption occupancy | house style: a shot whose captions fill it has no room to breathe |

The header states the pipeline in one line — `long · 612.4 s · 1920×1080 · 60 fps · dark theme ·
33 shots · 129 cues · no voice` — and reminds the reader that the captions carry the whole
explanation: there is no voice to fall back on, so a thing no cue says is a thing the video does
not say.

## `RENDER-REPORT.md` — what delivery leaves behind

One page per finished video: the status, a table of deliverables with **which file is the one to
watch**, what `verify_master.py` measured (the numbers, not the word "passed"), how the formulas
and geometry were independently checked against the notes, the caption pacing worst case, and any
Manim bug found and fixed. It is the file that answers "was this checked?" a year later, and it
is where a trap gets written down before it is promoted into `references/manim-traps.md`.

## Delivery and naming

- Projects are numbered by build order within their course:
  `~/academic-videos/<COURSE>/<nn>-<slug>/`. An abandoned project keeps its number and is marked
  `(no use)` rather than deleted — the number is referenced from later videos' briefs.
- The master is `out/final.mp4`, exported from Palmier Pro. **Any copy of it is named by course,
  lecture and concept**, not by project number — `MATH1030-L07-determinants.mp4`. Nobody
  remembers what project 04 was by the end of term.
- A project can sit at `awaiting-export` for a long time; that is a normal state. Do not read an
  assembled Palmier timeline or a full `out/` as a delivered video — check for an exported
  `out/final.mp4` and `RENDER-REPORT.md`.
