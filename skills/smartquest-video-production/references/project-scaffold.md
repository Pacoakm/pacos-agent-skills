# The project scaffold

`references/production-contract.md` defines the folder layout and what `video-plan.json` must
contain. This file covers what 25 built lessons put **inside** that layout: the four files the
skill does not ship, why each exists, and what carries from one lesson to the next.

The layout as it is actually built, with the additions marked:

```text
videos/<subject>/<nn>-<topic>/
├── brief.md              # the design record — objective, misconception, aha, DSE reasons,
│                         # the colour assignment, the camera decisions
├── make_plan.py          # + AUTHORS video-plan.json. Durations here, everything else derived
├── check_plan.py         # + the contract's invariants, runnable in the project
├── make_script.py        # + emits 講稿.md from the plan
├── video-plan.json       #   generated. Never hand-edited
├── 講稿.md               # + the Gate 1 artifact the user actually reads
├── narration-sheet.md    #   generated for the teacher at Gate 5
├── src/
│   ├── theme_boot.py     # + the only place the theme is switched on
│   ├── kit.py            # + this lesson's figures, and the series' memory
│   ├── script.py         #   the scenes
│   └── captions.py       #   generated by build_captions.py — do not hand-edit
├── tools/                #   installed by tools/install.py
├── vendor/               # + only when the lesson is bundled for another machine
├── storyboard/  audio/  out/
└── RENDER-REPORT.md      # + written at delivery
```

## `src/theme_boot.py` — the only place the theme is switched on

```python
sq.use_light()                 # ← the theme answer given at Gate 1
from smartquest_theme import *  # ← must come AFTER
```

`use_light()` must run **before** the star import, because the import copies the values out. Get
the order wrong and half the lesson is dark-theme; nothing raises. So every module imports the
palette from `theme_boot`, never from `smartquest_theme` directly, and the file names in its
docstring which theme was approved at Gate 1.

It also resolves the theme from `../vendor/` when that directory exists and falls back to
`~/.claude/skills/smartquest-video-production/scripts` otherwise — that one line is what makes a
bundle self-contained.

## `src/kit.py` — the lesson's figures, and the series' memory

Every project has one. It holds three things, and the reason it is a file rather than code inside
`script.py` is that all three are exactly what drifts between shots:

1. **The question band.** The stem is on every shot of an example (hard rule 23), so it is built
   **once**, read from `video-plan.json`, and every scene asks for it by question id rather than
   re-typing the string (contract invariant 10). A re-typed stem is how a band changes width
   halfway through an example.
2. **The pens.** The colour assignment recorded in `brief.md` is written down once, as names, so
   no scene ever picks a colour by hand (hard rule 6).
3. **The apparatus** — the figure builders for this lesson's subject.

Two conventions that matter more than they look:

**Layout helpers are copied from the previous lesson unchanged.** `panel()`, `centred()`,
`fit_figure()`, `mrow()`, `derivation_ref()`, `solution_page_ref()` are carried forward verbatim,
not re-derived. The library is one series: a helper that drifts is a helper that puts the stem
two pixels left of where it was in the lesson the student watched yesterday. If a helper genuinely
needs to change, change it **and** say which earlier lessons now differ.

**Every builder returns its parts named, and adds nothing.** A `thermometer()` hands back its
bulb, stem, column and scale as named pieces; the scene decides which of them are givens (on from
the first frame) and which are derived (drawn on the beat that produces them), because hard rule
18 makes that a per-shot decision. A builder that calls `self.add()` has taken that decision away.

**The apparatus is established once per subject and reused.** The Physics set was built in
`dse-physics/02-temperature-heat-internal-energy` for I(a) and is meant to serve I(b)–I(d):
`thermometer`, `scale_bar`, `particles`, `meter`, `bar`, `beaker`/`cup`/`tub`/`basin`, `heater`,
`kettle`, `clock`, `hand`, `can`, `block`, `sparkler`, `drop`, `flow`, plus small icons. When a
new lesson needs an apparatus that exists, import it; when it needs a new one, build it to the
same contract so the next lesson inherits it.

## `make_plan.py` — the plan is generated, never hand-edited

Only two kinds of number are authored: **shot durations and cue durations**. Every absolute
timecode, every derived field and the whole JSON are computed from them, so the plan cannot drift
from the script, and a re-timed shot cannot leave a stale `start` three shots later.

Two habits worth copying:

- A `STATUS` constant at the top carries the pipeline state into the plan, advanced **only when
  the user has actually approved the gate before it** — `awaiting-user-export`, and so on.
- **Decisions are recorded as comments beside the value they changed.** For example: the question
  band first measured 24% of frame height against its 22% cap; moving one given from the part into
  the stem — where the paper would put it anyway — brought it to 20.1% with the section tag kept.
  The physics and the answer were untouched. Six months later that comment is the only record of
  why the stem reads the way it does.

## `check_plan.py` — the contract, runnable

A per-project script that re-checks the production contract's invariants against the generated
plan: timeline continuity, whole frames, cue containment, the 4.0 字/秒 budget, the 25% still
floor, the 4.0 s recap page, the 3–4 s title card. Run it after every `make_plan.py` run and
before every gate. It reuses `scripts/build_captions.py`'s `weight()` so the 字數 it counts is
the same 字數 the caption builder counts — never re-implement the counter.

## `講稿.md` — the Gate 1 artifact the user actually reads

`make_script.py` emits it from the plan. Per shot: the timecode range, the section tag, the
register, the still time with its percentage, what is on the picture, and a cue table —
時間 · 秒 · 字數 · 字/秒 · 中文（書面語）· English.

Which numbers are gates and which are house style, because reporting the wrong one is its own
failure (hard rule 35):

| Number | What it is |
|---|---|
| **4.0 字/秒** | the gate — `check_plan.py` fails the plan above it |
| **25% still** | the gate — contract invariant 6 |
| 3.5 字/秒 | house style: scripts are *authored* here so a slower teacher still fits |
| ≤ 90% speech occupancy | house style: a shot whose speech fills it has no room to breathe |

The header states the pipeline in one line — `long · 601.0 s · 1920×1080 · 60 fps · light theme ·
33 shots · 129 cues` — and reminds the reader that the teacher speaks the 中文 line with the
subject terms said in English. That is the sentence that stops a narrator translating the terms.

## `RENDER-REPORT.md` — what delivery leaves behind

One page per finished lesson: the status, a table of deliverables with **which file is the one to
watch**, what `verify_master.py` measured (the numbers, not the word "passed"), how the geometry
was independently checked, the caption pacing worst case, and any Manim bug found and fixed. It
is the file that answers "was this checked?" a year later, and it is where a trap gets written
down before it is promoted into `references/manim-traps.md`.

## Delivery and naming

- Projects are numbered by build order: `videos/<subject>/<nn>-<topic>/`. An abandoned project
  keeps its number and is marked `(no use)` rather than deleted — the number is referenced from
  other lessons' briefs.
- **Finished masters leave the project tree.** They are copied out to the delivery folder named
  by the **syllabus topic**, not the project number — `4.4+4.5-function-and-graphs.mp4`,
  `11-solving-triangles.mp4`. Nobody outside the build knows what project 17 was.
- A project can sit picture-locked and undelivered for a long time; that is the normal state
  while a teacher's recording is pending. Do not read a full `out/` as a delivered lesson —
  check the delivery folder and `RENDER-REPORT.md`.
